## Security controls addressed

| Control | Requirement | How addressed |
|---------|-------------|---------------|
| SI-10 | Input validation on all API parameters | express-validator chains on `ref` and `invoice`; reject if both absent |
| AC-3 | Access enforcement | Route-level; credentials and limits read from `process.env`, never hardcoded |
| AU-6 | Audit review | Compliance headers (`X-Function`, `X-Owner`, `X-Control`, `X-Reviewed`) on every v2 response |
| PCI Req. 6.5.1 | Injection attack prevention | All SQL uses `db.prepare('...').get(param)` — no string concatenation |

## Intended differences from legacy

The v2 endpoints are behaviourally identical to the legacy endpoints on all observable paths. The only intentional differences are:

1. **Parameterized SQL** — eliminates SQL injection. Output is unchanged.
2. **Input validation** — `express-validator` enforces `max: 50` on both params. Inputs longer than 50 chars were never produced by any documented caller.
3. **Compliance response headers** — `X-Function`, `X-Owner`, `X-Control`, `X-Reviewed` added to every response.
4. **Environment-sourced config** — `APPROVAL_LIMIT_CENTS` and `AS_OF_DATE` read from `process.env` with fallback to the legacy hardcoded values.
